Gateway JWT Structure

The gateway issues its own JWT — NOT the Keycloak token.

JWT Payload 
{
  "iss": "api-gateway",          // issuer — must match in backend JWT strategy
  "aud": ["sema-core-service"],  // audience — must include SERVICE_ID of target
  "sub": "<keycloak-user-id>",
  "jti": "<unique-token-id>",   // validated against Redis blacklist
  "email": "user@kaeyros.com",
  "name": "Jordan Yeinko",
  "roles": ["admin", ...],
  "iat": 1718000000,
  "exp": 1718003600              // 1 hour default
}

Service-to-Service Auth (HMAC)

When the gateway forwards requests to backend services, it adds two extra headers.

HeaderValue
x-gateway-signature HMAC-SHA256("{timestamp}:{method}:{path}", GATEWAY_SHARED_SECRET)
x-gateway-timestamp Unix timestamp in milliseconds (used in signature + replay-attack prevention)

Gateway side — signing the request (Express) 
// In the gateway proxy middleware, before forwarding to backend:
import crypto from 'crypto';

const timestamp = Date.now().toString();
const signature = crypto
  .createHmac('sha256', process.env.GATEWAY_SHARED_SECRET)
  .update(`${timestamp}:${req.method}:${req.path}`)
  .digest('hex');

// These headers are added to the forwarded request:
proxyReq.setHeader('x-gateway-timestamp', timestamp);
proxyReq.setHeader('x-gateway-signature', signature);

Backend side — verifying the signature (NestJS middleware) 
import { Injectable, NestMiddleware, UnauthorizedException } from '@nestjs/common';
import { createHmac } from 'crypto';

@Injectable()
export class GatewayMiddleware implements NestMiddleware {
  use(req: any, res: any, next: () => void) {
    const timestamp = req.headers['x-gateway-timestamp'] as string;
    const signature = req.headers['x-gateway-signature'] as string;

    if (!timestamp || !signature) {
      throw new UnauthorizedException('Missing gateway headers');
    }

    // Reject requests older than 5 minutes (replay attack prevention)
    if (Date.now() - parseInt(timestamp) > 300_000) {
      throw new UnauthorizedException('Request timestamp expired');
    }

    const expected = createHmac('sha256', process.env.GATEWAY_SHARED_SECRET)
      .update(`${timestamp}:${req.method}:${req.path}`)
      .digest('hex');

    if (signature !== expected) {
      throw new UnauthorizedException('Invalid gateway signature');
    }

    next();
  }
}

Route Registration — Adding a New Backend

Every backend service must be declared in the gateway's route files before it can receive forwarded requests. There are four files to update — one for local development and one per deployed environment.

Without a matching entry in these files the gateway returns 404 Not Found for every request to that service, regardless of authentication state.

FileUsed when
routes.yml (repo root)Local development — bun run start:dev
.github/routes/routes-dev.ymlDev environment (CI/CD pipeline)
.github/routes/routes-stg.ymlStaging environment (CI/CD pipeline)
.github/routes/routes-prod.ymlProduction environment (CI/CD pipeline)

Add an entry for your service in routes.yml (local). The path is the URL prefix clients use; target is where the gateway forwards the request.

routes.yml — local development 
routes:
  - path: "core-service"
    target: "http://localhost:3003"
    rewritePath: true
  # Add your new service here:
  - path: "my-new-service"
    target: "http://localhost:3005"   # your service's local port
    rewritePath: true

For each deployed environment, add the same entry pointing to the deployed URL.

.github/routes/routes-dev.yml (repeat pattern for stg and prod) 
routes:
  - path: "core-service"
    target: "https://core-dev.sem-a.com"
    rewritePath: true
  # Add your new service:
  - path: "my-new-service"
    target: "https://my-service-dev.sem-a.com"
    rewritePath: true

The path value in routes.yml must match the SERVICE_ID environment variable in your backend service — the gateway uses it to build the JWT aud claim and to verify that the token is destined for your service.

Custom Request Headers — CORS & Forwarding

If your backend service needs a custom HTTP header sent by the frontend (e.g. x-tenant-id, x-workspace-id), you must register it in two separate places in the gateway source code. Missing either step causes a different failure.

This is a frequent integration trap. The CORS fix and the forwarding fix are independent — each one alone is not enough. Both must be done together.

1

Add the header name to DEFAULT_ALLOWED_HEADERS in src/common/constants/security.constants.ts. This tells the browser the header is allowed in CORS preflight responses. Without this, the browser blocks the request before it reaches any server.

src/common/constants/security.constants.ts 
DEFAULT_ALLOWED_HEADERS: [
  'Content-Type',
  'Authorization',
  'Cookie',
  'x-credential-id',
  'x-tenant-id',      // ← add your header here
] as const,
2

Add the same header name to headersToForward in src/modules/proxy/services/proxy-request-handler.service.ts. This tells the proxy to actually pass the header through to your backend. Without this, the gateway receives the header from the browser but silently drops it before proxying.

src/modules/proxy/services/proxy-request-handler.service.ts 
const headersToForward = [
  'x-user-id',
  'x-user-email',
  'x-user-roles',
  'x-credential-id',
  'x-tenant-id',      // ← add your header here too
  'authorization',
];
If you only do step…Symptom
Step 1 only (CORS, not forwarding)Browser preflight passes, but your backend receives the request without the custom header — as if it was never sent.
Step 2 only (forwarding, not CORS)Browser preflight is blocked — "Request header field x-tenant-id is not allowed by Access-Control-Allow-Headers in preflight response". Request never reaches the server.

Note: the WebSocket upgrade path has its own header-building logic. Custom headers added to headersToForward are forwarded for HTTP requests only. For WebSocket connections, only JWT-derived headers (x-user-id, x-user-email, x-user-roles, x-credential-id) are forwarded by the upgrade service.

Deployed Frontend Origins — CORS Allow-List

The gateway reads allowed frontend origins from two sources that are merged at startup. Deployed environment URLs should go in the environment variable — not in the source code — so they can be configured per environment without a code change.

In source code

DEFAULT_ORIGIN in security.constants.ts — for localhost dev URLs that are always needed. Do not add deployed URLs here.

Via environment variable

CORS_ORIGIN env var on the deployed gateway — comma-separated list of allowed origins. Add each new deployed frontend URL here.

Gateway .env — staging example 
CORS_ORIGIN=https://dashboard-stg.sem-a.com,https://order-stg.sem-a.com,https://univers-bulk-stg.sem-a.com

If a new deployed frontend's requests are being blocked with "CORS origin not allowed" (403), add its URL to CORS_ORIGIN on the deployed gateway and restart. No code change or redeployment of the gateway code is needed.

WebSocket & Socket.io Routing

The gateway automatically handles WebSocket upgrade requests using the same routes.yml entries — no extra configuration is needed beyond registering the route. The WebSocketUpgradeService intercepts HTTP Upgrade requests before they reach NestJS and proxies them to the correct backend.

1

Your backend exposes a Socket.io server (e.g. NestJS @WebSocketGateway() with a namespace). No special gateway configuration needed — the route entry in routes.yml covers both HTTP and WebSocket.

2

The frontend connects with the gateway's base URL as the Socket.io server, specifying the service path:

Frontend — Socket.io connection 
import { io } from 'socket.io-client';

const socket = io(SSO_BASE_URL, {
  path: '/api/my-service/socket.io',   // SERVICE_ID in the path
  auth: { token: accessToken },        // JWT for authentication
  transports: ['websocket'],
});
3

The gateway authenticates the upgrade using either the Bearer token in the Authorization header, or the signed session cookie. It then forwards these headers to your backend:

x-user-idresolved from JWT or session
x-user-emailresolved from JWT or session
x-user-rolesresolved from JWT or session
x-credential-idresolved from JWT or session
x-gateway-signatureHMAC — your backend must verify this

Custom headers added to headersToForward (for HTTP proxying) are not forwarded for WebSocket connections. The WebSocket upgrade path uses its own header builder. If your Socket.io backend needs tenant context, pass it via the token payload or the Socket.io auth / query fields instead.

Public Endpoints — Bypassing Auth (Webhooks)

Some backend endpoints must be reachable by external services (Meta, payment providers, monitoring systems) without a gateway JWT. Two independent bypass mechanisms must both be configured.

1

In your NestJS backend, decorate the controller method with @Public(). This tells the JwtAuthGuard to skip JWT validation for that route.

your-service/src/modules/webhooks/webhook.controller.ts 
@Public()
@Post('webhooks/meta/status')
async handleMetaWebhook(@Body() body: MetaWebhookDto) { ... }
2

Also exclude the path from GatewayAuthMiddleware in your backend's app.module.ts. This middleware runs before guards and validates the HMAC gateway signature — external callers (Meta, payment APIs) never send this signature, so they would be blocked at that layer even if the JWT guard is skipped.

your-service/src/app.module.ts 
consumer
  .apply(GatewayAuthMiddleware)
  .exclude(
    { path: 'credits/webhook', method: RequestMethod.POST },
    { path: 'webhooks/meta/status', method: RequestMethod.POST },
  )
  .forRoutes('*');

Do not rely on @Public() alone for external webhooks. If the path is not excluded from GatewayAuthMiddleware, the middleware returns 401 Unauthorized before the guard is even reached, because there is no valid HMAC signature on the inbound request from Meta or a payment provider.
